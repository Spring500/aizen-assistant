# 持久化资源错误隔离

本文面向实现与维护持久化系统的开发者，规定目录型 Store 的错误隔离协议、会话错误的交互行为，以及防止新持久化入口绕过协议的检查规则。

核心约束是：单个条目损坏、不兼容、冲突或暂时不可读时，其他健康条目与所属子系统仍可使用。条目错误不得阻止 Agent 启动、新建会话或打开其他会话。

本文不为旧会话格式提供迁移或兼容层，也不解释已经删除的旧权限记录语义。`--collect-permission-gaps` 的清理由独立任务处理。

---

## 1. 分层职责

持久化条目从磁盘进入界面时依次经过 Store、Core 和 TUI。三层职责如下：

| 层级 | 职责 | 禁止行为 |
|---|---|---|
| Store | 读取条目，执行本业务的格式与语义校验，逐条隔离错误，返回统一目录结果 | 因单个条目错误而使整个列表失败 |
| Core | 根据条目能力执行正常打开、只读强制打开、恢复等操作 | 根据错误码字符串推断可执行操作 |
| TUI | 展示 Core 返回的状态、问题标识和可用操作 | 直接读取业务文件或自行解释错误码 |

业务校验仍由各 Store 实现。统一协议不取代业务规则，而是约束业务规则如何声明错误、如何返回失败条目，以及上层如何消费结果。

## 2. 统一目录协议

统一类型定义在 `packages/core/resource-catalog.ts`：

| 类型 | 作用 |
|---|---|
| `EntryState` | 表示条目的总体状态：`healthy`、`degraded` 或 `unavailable` |
| `ResourceIssue` | 提供稳定的 `code`、类别、中文标识和诊断消息 |
| `ResourceCapabilities` | 明确条目是否可以正常打开、写入、只读强制打开或恢复 |
| `CatalogResult` | 同时返回全部条目和目录级问题，使单条错误可以作为条目结果返回 |

`EntryState` 用于概括状态，不决定具体行为。Core 和 TUI 必须读取 `ResourceCapabilities`，不能从状态或错误码反推能力。

### 2.1 问题定义

每个业务通过 `defineIssues()` 集中定义自己的问题：

```ts
const sessionIssues = defineIssues({
  "session.invalid_json": {
    category: "syntax",
    label: "内容损坏",
  },
})
```

同一张定义表同时提供两种约束：

- 业务内部通过 `create()` 创建问题，TypeScript 在编译期检查 `code`；
- RPC、插件或磁盘反序列化得到的字符串通过 `has()` 做运行时检查。

业务内部不得手写 `ResourceIssue`，外部输入也不得仅依赖 TypeScript 类型断言。各 Store 可以定义本业务的问题类型和检查代码，但必须通过统一结构向上层返回。

## 3. 会话错误与行为

会话列表按问题类型显示不同标识，并由能力决定可执行操作：

| 标识 | 典型原因 | 正常打开 | 只读强制打开 | 恢复为新会话 |
|---|---|---:|---:|---:|
| `[不兼容]` | 记录不能通过当前会话结构校验 | 否 | 是 | 是 |
| `[内容损坏]` | 文件中存在无法解析的 JSON 行 | 否 | 是 | 是 |
| `[未完整写入]` | 进程中断留下无法解析的最后一行 | 是 | 否 | 否 |
| `[ID 冲突]` | 多个文件声明同一个会话 ID | 否 | 是 | 是 |
| `[读取失败]` | 文件或文件状态无法读取 | 否 | 否 | 否 |
| `[使用中]` | 其他 Agent 持有该会话的写租约 | 否 | 否 | 否 |

只读强制打开和恢复要求文件仍有有效文件头及可识别记录；缺少这些内容时，相应能力保持关闭。TUI 直接使用实际能力决定是否显示操作，不把上表当作额外判定逻辑。

只读强制打开只投影能够按当前格式严格识别的记录，不获取写租约，也不修改原文件。恢复使用这些记录创建一个新的当前格式会话，原文件保持不变。两种操作都不会尝试解释旧记录的权限语义。

### 3.1 未完整尾行

只有同时满足以下条件的行才视为未完整写入：

1. 位于文件最后一行；
2. 文件末尾没有换行符；
3. 该行无法解析为 JSON。

Store 在读取时忽略该行，会话仍可正常打开和继续写入。下一次追加前，Store 在写租约内将文件截断到最后一个完整换行处。完整但不兼容的 JSON 记录不属于未完整尾行，不得自动删除。

## 4. 防止新增入口绕过隔离

统一协议只有在所有持久化入口都受检查时才有效。仓库通过登记表、组合根和静态检查共同约束入口：

- `packages/core/storage-registry.ts` 登记所有持久化资源、实现文件、资源形态和允许的生产构造位置；
- `packages/core/data-stores.ts` 与 `packages/pi-adapter/data-stores.ts` 是生产 Store 的组合根；
- `filesystemAccessPolicy` 登记允许直接访问文件系统的文件及其用途；
- `scripts/repo/check-storage-isolation.ts` 检查未登记的 Store、Recorder、直接文件系统访问和越过组合根的实例化。

`bun run check:storage-isolation` 已纳入 `bun run verify`。新系统若新增上述入口但未登记，持续集成会直接失败。

静态检查负责发现可能绕过架构的代码入口，故障注入契约负责确认运行时行为。两者不能互相替代。

## 5. 新增目录型 Store

新增目录型 Store 时必须完成以下工作：

1. 在业务内通过 `defineIssues()` 声明问题定义表；
2. 让列表接口返回 `CatalogResult`，将单条读取或校验错误转换为带问题和能力的条目；
3. 在 `storage-registry.ts` 登记资源、实现和允许的构造位置；
4. 通过对应的 `DataStores` 组合根创建生产实例；
5. 在 `tests/core/storage-isolation-contract.test.ts` 增加故障注入用例，断言坏条目可见、健康条目仍可列出和打开；
6. 在界面层只消费问题标识和能力，不重新实现业务判断。

文档型、追加日志型和缓存型资源同样需要登记，但不强制伪装成条目目录。其故障策略应按资源形态单独设计，并保证非必要业务文件的错误不会阻止 Agent 启动。

## 6. 验证

```powershell
bun run check:storage-isolation
bun test tests/core/storage-isolation-contract.test.ts
bun run docs:build
bun run verify
```

当前故障注入契约覆盖会话文件、视图目录和 Skill 来源目录。
