# AizenAssistant 技术路线图

本文档说明 AizenAssistant 的稳定设计、当前进度和后续开发顺序。实现细节以代码和对应阶段的设计文档为准；本文只记录影响整体方向的内容。

## 1. 产品目标

AizenAssistant 是基于 pi SDK 构建的 AI Agent 应用，提供可独立使用的终端界面和重点打磨的桌面界面。

项目重点解决两类问题：

1. **每轮额外消息**：模型请求发出前可加入零条或多条额外消息。所有实际发送的消息均写入会话；仅当轮使用的消息不进入后续请求。
2. **视图式上下文组织**：系统提示词、`AGENTS.md` 和 Skill 由用户选择的视图目录提供，不按工作目录层级隐式加载。

## 2. 路线设计原则

- 先完成可独立使用的核心，再建设桌面界面。
- 先验证高风险边界，再投入界面开发。
- 每个阶段都必须形成可运行、可验证的结果。
- TypeScript 承担业务逻辑；Rust 只管理桌面进程和字节转发。
- pi 和 OpenTUI 通过独立适配层使用，并锁定精确版本。
- 不修改 pi 源码，不把 pi 的会话格式作为产品数据格式。
- 分发产物不依赖用户预装 Node 或 Bun，并以单文件形式交付；无法满足时停止并重新确认分发形态。

## 3. 稳定设计

### 3.1 运行结构

```text
自研 TUI ───────────────────────────┐
                                    ▼
                              TypeScript 核心
                                    │
                                    ▼
                               pi adapter ── pi SDK

Vue 桌面界面 ── Tauri / Rust ── JSONL ── core-sidecar ── TypeScript 核心
```

- 终端界面与核心运行在同一进程。
- 桌面界面通过 `core-sidecar` 使用同一核心。
- 核心只依赖自有接口，不直接导入 pi 或 OpenTUI 类型。
- `core-sidecar` 负责命令和事件转换，不增加业务规则。

### 3.2 数据组织

正式产物默认使用可执行文件同目录的 `data`：

```text
data/
├─ auth.json
├─ models.json
├─ views.json                         M3 增加
└─ sessions/
   └─ <工作目录名称>-<路径哈希>/
      └─ <会话 UUID>.jsonl
```

- `auth.json` 保存认证信息，由程序维护。
- `models.json` 保存模型配置，由用户手工编辑；当前不提供配置界面。
- `views.json` 保存视图 ID 到实际目录的对应关系，计划在 M3 增加。
- 会话按工作目录分组；一个会话对应一个 JSONL 文件，不建立会话目录、附件目录或图片池。
- 源码开发命令默认使用 worktree 内的 `.aizen/dev-data`；直接运行源码时必须通过 `--data-dir` 指定数据目录。

### 3.3 会话记录

AizenAssistant 使用自有、带版本的会话格式。pi 会话只存在于内存中。

会话按发生顺序记录：

- 文件头；
- 模型变化；
- 视图变化；
- 每轮实际发送的消息；
- 助手消息和工具结果；
- 轮次完成、中止或失败状态；
- 上下文压缩摘要。

图片以 `mimeType` 和 Base64 数据直接写入消息。压缩只改变后续请求的运行时上下文，不删除或改写原始会话记录。

程序基础系统提示词、视图文件内容和工具列表不写入会话。恢复后按当前程序版本和当前视图重新装载；会话只记录各轮使用的视图 ID。

### 3.4 视图

`viewId: null` 表示空视图。非空视图计划在 M3 通过 `data/views.json` 定位实际目录：

```text
<视图目录>/
├─ system.md                  可选
├─ AGENTS.md                  可选
└─ skills/
   └─ <skill>/
      ├─ SKILL.md
      └─ 其他资源             可选
```

视图应遵循以下规则：

- 每轮开始前重新读取当前视图。
- 视图内容变化从下一轮开始生效，不保存历史副本。
- 视图可在两轮之间切换，不在正在执行的轮次中切换。
- 视图 ID 不存在、路径失效或内容无效时阻止新轮次。
- 不读取工作目录、父目录、用户目录或视图目录外的同类资源。

## 5. 已完成阶段

### M0 —— 仓库治理

建立版本约束、代码检查、PR 流程和主分支防误操作措施。所有里程碑通过 Draft PR 交付，由项目负责人审核和合并。

### M1 —— 架构可行性验证

验证 pi SDK、OpenTUI、WASM 和原生依赖可以共同编译为 Windows x64 Bun 单文件，并可在无 Node、无 Bun 的环境运行。验证 pi 资源覆盖、扩展和模型请求链路可用。

### M2 —— 核心与自举 TUI

建立无界面核心、pi adapter、OpenTUI 适配层和终端应用，完成：

- 连续多轮对话；
- 会话创建、自动保存、列表和恢复；
- 流式文字、思考和工具状态；
- 回复中止和失败记录；
- 模型选择与两轮之间切换；
- API 密钥认证和手工模型配置；
- 上下文压缩记录；
- 源码开发命令和数据目录参数；
- 单次、无状态的 `--plain` 模式；
- 使用终端原生 scrollback 的滚动式 REPL；
- 助手回复、工具调用及工具组的折叠管理。

M2 固定使用空视图，每轮记录 `viewId: null`。旧开发会话不提供迁移，格式变化后删除并重新生成。

## 6. 后续阶段

### M3 —— 上下文定制

**目标：** 完成两项核心定制能力，并继续由 TUI 验证真实行为。

**范围：**

- 增加 `data/views.json` 的读取和校验。
- 支持新建、恢复时选择视图，以及两轮之间切换视图。
- 每轮重新读取系统提示词、`AGENTS.md` 和 Skill。
- 支持预处理产生零条或多条额外消息。
- 保存所有实际发送的额外消息，并通过 `useLater` 控制是否进入后续请求。
- 验证现有折叠与全量回放机制可以正确呈现新增的上下文记录。

**完成条件：**

- 连续多轮观察证明，仅当轮消息没有进入下一轮。
- 修改视图内容后，下一轮使用新内容；旧轮次记录保持不变。
- 切换视图后，系统提示词、`AGENTS.md` 和 Skill 均来自目标目录。
- 视图失效时给出明确错误，且不发送模型请求。
- 压缩前的原始记录仍可完整读取。

### M4 —— 桌面进程边界

**目标：** 在建设桌面界面前，证明核心可以通过稳定的进程边界运行和分发。

**范围：**

- 建立版本化的 JSONL 命令、事件和错误格式。
- 建立 `core-sidecar`，复用现有核心和 pi adapter。
- Rust 只负责 sidecar 启停、标准输入输出转发和异常退出检测。
- stdout 只传输 JSONL，日志只写入 stderr。
- 严格按 `\n` 分帧，不在 `U+2028` 或 `U+2029` 处分行。
- 验证 sidecar 异常退出后的检测、重启和会话重新打开。
- 验证 Tauri、`core-sidecar` 和所需资源能否以单文件形式交付；若无法满足，停止并重新确认分发形态。

**完成条件：**

- 无界面测试可通过 JSONL 完成会话创建、多轮请求、中止和恢复。
- 分帧边界测试全部通过。
- sidecar 可编译为无需外部 Node 或 Bun 的 Windows x64 可执行文件。
- Rust 层没有会话、模型、视图或消息处理逻辑。

### M5 —— 桌面最小闭环

**目标：** 建立最小但真实的桌面运行链路，不提前扩展完整界面。

**范围：**

- 初始化 Vue、Vite 和 Tauri。
- 启动并管理 `core-sidecar`。
- 显示一条用户消息和流式助手回复。
- 支持中止当前回复。
- 显示 sidecar 启动失败、异常退出和协议错误。

**完成条件：**

- 桌面应用可完成一次真实模型请求和中止。
- 关闭窗口后 sidecar 不残留。
- sidecar 异常退出时界面明确提示并可恢复。
- Windows 构建产物在无 Node、无 Bun 环境运行。

### M6 —— 桌面核心功能与交互

**目标：** 将 M3 已验证的核心能力完整呈现在桌面界面中。

**范围：**

- 会话创建、列表、恢复和切换；
- 服务商认证、模型选择和模型切换；
- 视图选择、切换和错误提示；
- 多轮消息、思考过程和工具执行展示；
- 消息输入、中止和错误恢复；
- 界面状态与核心状态一致，不以渲染结果代替业务状态。

**完成条件：**

- TUI 已验证的核心能力均可从桌面界面使用。
- 界面重启后可恢复已有会话。
- 相同操作在 TUI 和桌面界面中产生一致的核心记录。
- 认证信息不出现在界面日志、协议日志或错误详情中。

### M7 —— 桌面体验完善

**目标：** 在不改变核心行为的前提下，集中完善桌面界面的信息组织和操作体验。

**范围：**

- 明确区分用户消息、助手消息、思考过程、工具执行和错误状态；
- 完善长会话滚动、长内容阅读、窗口缩放和输入焦点行为；
- 统一会话、模型、认证和视图选择流程；
- 处理空状态、等待状态、中止状态和恢复状态；
- 根据真实使用结果调整布局、反馈和操作顺序。

**完成条件：**

- 日常多轮开发无需借助终端界面完成操作。
- 关键状态具有明确且一致的视觉和操作反馈。
- 长会话、长工具输出、中文输入和窗口缩放不影响主要操作。
- 项目负责人完成真实任务验收并确认桌面体验达到发布要求。

### M8 —— Windows 分发验收

**目标：** 形成可交付的 Windows x64 版本。

**范围：**

- 固化构建、打包和版本信息生成流程。
- 在无 Node、无 Bun 的干净环境验证单文件产物。
- 验证数据目录可写，并在删除应用目录后不残留认证、模型、会话或视图配置。
- 验证升级不会静默改变模型、会话或视图数据。
- 完成中文输入、粘贴、滚动、多轮对话、工具执行、中止和恢复的人工验收。

**完成条件：**

- 自动构建可重复产生同类分发产物。
- 干净环境中所有核心功能可用。
- 最终交付物为单文件，不要求用户另行复制 sidecar 或资源文件。
- 不向 `%APPDATA%`、`%LOCALAPPDATA%` 或 `~/.pi` 静默写入产品数据。
- 分发产物和数据位置均有明确说明。

## 7. 跨阶段验证

以下行为不能只依赖单元测试，必须在相关阶段进行多轮人工观察：

- 仅当轮消息确实进入当前请求，且下一轮不再出现。
- 视图切换和内容修改确实影响下一轮请求。
- 会话恢复后的模型上下文与保存记录一致。
- 中止不会自动重试，部分回复和结束状态可以恢复。
- JSONL 在边界字符和进程异常情况下仍保持完整。
- 最终产物在无 Node、无 Bun 环境运行。

## 8. 交付规则

- 每个里程碑使用独立分支和 Draft PR。
- Agent 不得将 PR 转为 Ready，不得合并或发布。
- 项目负责人负责设计确认、真实环境验收和最终合并。
- 私有方案、实施计划、凭证、会话和构建产物不得加入版本库。
- pi 或 OpenTUI 升级必须单独进行，并在升级前审阅破坏性变更。
