# 自举套件实现规格

本文是[《自举套件使用说明》](自举套件-使用说明.md)的技术对应文档，面向实现与维护自举套件的开发者。用户可见行为以《使用说明》为准，本文不重复，只描述内部结构、接口契约与边界条件。

---

## 1. 总体结构

Mock Server 收到请求后分四层处理：

```
HTTP 请求
  → 路由层：按路径识别协议，按请求体 model 字段选择行为
  → 行为层：行为模块产出协议无关的抽象事件流
  → 编码层：抽象事件流编码为对应协议的 SSE
  → HTTP 响应
```

层与层严格分离：**行为模块不感知协议，编码器不感知行为。** 新增行为不需要改编码器，新增协议不需要改任何行为。

### 1.1 设计约束

三条约束贯穿全部实现：

| 约束 | 含义 |
|---|---|
| **无状态** | 行为只依据当次请求内容产出结果，服务端不保存任何跨请求状态 |
| **行为即模块** | "哪个模型做什么"由注册表决定，Server 不内置任何模型语义 |
| **协议无关** | 行为产出抽象事件，协议差异全部收敛在编码层 |

无状态约束的直接后果：多轮工具流程的推进必须从请求携带的对话历史推导，不得用计数器或会话缓存。这与真实模型服务一致，也使并发会话、服务重启、测试并行执行天然安全。

行为即模块约束的直接后果：会话命名、权限审核这类子 Agent 的应对，是**某个行为模块的职责**，而非 Server 的路由分支。Server 不识别 `set_session_title` 之类的工具名。将来新增子 Agent，只需新增行为模块与模型条目，Server 代码不动。

---

## 2. 路由层

### 2.1 协议识别

按请求路径识别，两种协议的路径互不重叠：

| 路径 | 协议 | 套件中配置的 baseUrl |
|---|---|---|
| `POST /v1/messages` | `anthropic-messages` | `http://127.0.0.1:39527` |
| `POST /v1/chat/completions` | `openai-completions` | `http://127.0.0.1:39527/v1` |

路径由各官方 SDK 硬编码，与 `baseUrl` 直接字符串拼接，因此无需为协议加路径前缀。后续扩展 `openai-responses`（`/v1/responses`）与 `google-generative-ai`（`/v1beta/models/{id}:streamGenerateContent`）时同样不会冲突。

其余路径返回 404。

### 2.2 行为选择

从请求体 `model` 字段取模型 ID，在静态注册表中查找对应行为模块。未注册的模型 ID 返回 404，错误信息中列出全部已注册模型，便于排查套件配置与注册表不一致。

注册表是显式的 `Record<string, MockBehavior>` 字面量，不做目录扫描。行为是代码而非数据，静态注册可获得契约校验与重命名安全。

### 2.3 与既有测试装置的关系

现有 `tests/utils/mock-server.ts` 的 `startMockServer` 及其 `take` / `handle` / `handleModel` / `requests` 接口全部保留，语义不变。行为注册表作为新增的分发层，优先级低于 `handleModel` 与 `handle`：既有测试显式设置的处理器仍然优先生效。

## 3. 行为层

### 3.1 接口契约

```ts
type MockBehavior = (context: MockRequestContext) => AsyncIterable<MockEvent>
```

`MockRequestContext` 提供已归一化的请求内容：`model`、`system`、`messages`、`tools`、原始 `body`。**归一化在路由层完成**，两种协议的请求体经统一后交给行为模块，因此行为模块不需要区分请求来自哪种协议。

返回异步可迭代对象而非数组，使 `delay` 与 `hang` 可以自然表达为产出事件之间的等待。

### 3.2 抽象事件

| 事件 | 语义 |
|---|---|
| `thinking` | 思考内容增量 |
| `text` | 回复文本增量 |
| `tool` | 一次工具调用，含 `callId`、`name`、`arguments` |
| `finish` | 本轮结束，含停止原因与 token 用量 |
| `error` | HTTP 层错误，含状态码与消息 |

`delay` 与 `hang` 不是事件：前者在行为模块内部 `await`，后者表现为迭代器永不产出。两者都由 `AbortSignal` 中断，对应用户取消。

`error` 事件必须是流中第一个事件。SSE 响应头一旦发出，HTTP 状态码不可更改；若行为模块在产出内容后才产出 `error`，编码层抛出实现错误而非静默降级。

### 3.3 内置行为模块

三个模块地位平等，均以相同接口实现，无任何一个享有特殊地位。

| 模型 ID | 模块职责 |
|---|---|
| `mock-dsl` | 解析最后一条 user 消息为指令并执行；解析失败输出固定提示与原文 |
| `mock-naming` | 调用 `set_session_title`，标题为 `[MMDD-HHmm] <关键字>` |
| `mock-review` | 调用 `submit_permission_review`，按意图暗语裁决 |

后两个模块需遵守对应子 Agent 的协议契约，违反会触发调用方的纠错重试并最终失败：

- `set_session_title`：`title` 为单行、非空、不超过 80 字符。关键字取自 user 消息，压缩空白后截断至总长度不超限。调用方最多纠正 3 轮（`packages/pi-adapter/session-title-generator.ts`）。
- `submit_permission_review`：`decision` 取 `allow` / `deny` / `needHumanReview` 之一，`reason` 非空且不超过 500 字符。调用方传入的 user 消息是 `AiReviewRequest` 的 JSON 序列化结果，暗语从其 `declaredIntent` 字段读取。调用方最多纠正 2 轮（`packages/pi-adapter/permission-reviewer.ts`）。

模块必须一次只调用一个工具，两个调用方都拒绝多个工具调用。

## 4. 指令解析

用户可见语法见《使用说明》第 4 节，本节只描述解析与轮次推导机制。

### 4.1 解析

解析器是纯函数：文本进，指令序列出，无副作用、不接触网络与文件系统，可独立单测。

判定为指令的条件是**所有非空行都以已知动词开头**（块内文本除外）。任一行不满足即整体判定为解析失败，退化为回显。不采用前缀标记，使日常使用无额外负担。

块结构 `<<<` / `>>>` 支持嵌套，`edit` 的 `old` / `new` 块即嵌套一层。解析器按嵌套深度配对，不做简单的首个结束标记匹配。

意图字段超过 50 字符时截断而非报错。该上限来自工具契约中 `declaredIntent` 的定义（`packages/pi-adapter/session-runtime.ts`）。

### 4.2 轮次推导

一条指令序列可能跨多轮响应。切分点由**数据依赖**决定，不由人工标注：

> 顺序执行指令，`tool` 指令累积待发；一旦遇到引用了尚无结果的 `{{名.Result}}` 的指令，在此处结束本轮。

因此连续且互不引用的工具调用会在同一轮并行发出，符合真实模型行为。

推进游标的依据是**对话历史中已存在的工具结果**：

1. 取最后一条 user 消息，解析为指令序列；
2. 扫描该消息之后的历史，收集全部 `tool_result` 及其 `tool_use_id`；
3. 跳过 `callId` 已在结果集合中的 `tool` 指令，从首个未执行的指令继续；
4. `{{名.Result}}` 用结果集合中对应内容替换。

这要求 `tool_use` 的 `callId` 可被识别。**实现采用用户指定的调用名作为 `callId`**，使推导精确且无需计数。

协议只要求 `callId` 在会话内唯一，不限定格式。但 Aizen 经由 pi 转发工具调用，若 pi 重写了 `callId`，上述方案失效。**因此实现的第一步是验证 pi 是否原样透传 `callId`。** 若不透传，退化方案为按 `tool_result` 出现顺序与指令中 `tool` 出现顺序对齐推导；该方案在工具调用失败或乱序时精度下降，是明确的次优选择。

### 4.3 解析失败

输出固定提示 `用户输入无法解析，原样输出结果如下：` 加换行加原文。原文不截断——这是用户可见的诊断信息，截断会妨碍排查。

会话命名 Agent 收到的正是主对话首条 user 消息（`packages/core/aizen-core.ts` 中 `#startSessionNaming`），即指令原文。命名由 `mock-naming` 模块独立处理，不受 `mock-dsl` 的解析结果影响。

## 5. 编码层

每种协议一个编码器，输入抽象事件流，输出 SSE 字节流。

### 5.1 两种协议的差异

| | `anthropic-messages` | `openai-completions` |
|---|---|---|
| 事件命名 | 有 `event:` 行 | 无，仅 `data:` |
| 结束标记 | `message_stop` 事件 | `data: [DONE]` |
| 文本增量 | `content_block_delta` / `text_delta` | `choices[].delta.content` |
| 工具调用 | `content_block` 为 `tool_use`，参数经 `input_json_delta` 分片 | `delta.tool_calls[].function.arguments` 分片，`finish_reason` 为 `tool_calls` |
| 思考内容 | `thinking` 类型 content block | 非标准字段，按服务商而异 |

差异不止于路径与字段名，涉及整条流的结构，因此必须分层而非条件分支。

### 5.2 编码器契约

编码器只做格式翻译，不改变语义：事件顺序、文本内容、工具参数原样映射。不得在编码器内注入行为逻辑，否则两种协议会产生行为差异，失去交叉验证的价值。

每个编码器需有独立单测，断言产出的 SSE 可被对应官方 SDK 正确解析。

## 6. 数据模板与运行实例

| | 路径 | 入库 | 可写 |
|---|---|---|---|
| 模板 | `tests/fixtures/mock-data-templates/<套件名>/` | 是 | 视为只读 |
| 运行实例 | `<工作区根>/mock-data/` | 否 | 是 |

模板入库使套件可版本化、可评审；运行实例不入库，使应用运行时改写偏好、写入会话记录不污染工作区。这一分离是必要的：`preferences.json` 会被应用改写，若直接以入库目录启动，每次运行都会产生工作区变更。

`mock-data/` 通过 `.gitignore` 排除。

套件之间完全自包含，无基础层、无合并机制。重复内容是有意为之：套件数量有限，自包含带来的可读性与可独立修改性，优于消除重复。

## 7. 启动器

`scripts/dev/run-mock.ts`，经 `bun run dev:mock` 调用。

流程：

1. 解析套件名与 `--keep`；套件不存在时列出可用套件并退出；
2. 未指定 `--keep` 时删除并重建 `mock-data/`，从模板复制；
3. 在固定端口 `39527` 启动 Mock Server；端口占用直接失败退出；
4. 以 `mock-data/` 为数据目录启动 TUI；
5. TUI 退出后关闭 Server。

**端口固定且占用时不回退。** 套件中的 `baseUrl` 是静态入库内容，动态换端口会使配置失效；快速失败并提示，优于启动一个连不上的环境。

Server 与 TUI 同进程运行，`Bun.serve` 不阻塞事件循环，避免子进程生命周期管理。

## 8. 扩展方式

| 需求 | 改动 |
|---|---|
| 新增一种模型行为 | 实现 `MockBehavior` 模块，注册到注册表，在套件中加模型条目 |
| 新增一套配置场景 | 在 `mock-data-templates/` 下新建自包含目录，无需改代码 |
| 新增一种协议 | 实现编码器与请求归一化，在路由层登记路径，套件中加供应商条目 |
| 新增一类子 Agent 支持 | 等同"新增一种模型行为"，Server 与既有模块不动 |

前两项是最常见的扩展，均不需要理解本文其余内容。
