# AizenAssistant 面向用户文档差异化调研

本文基于 2026-07-30 的代码、测试和代表性竞品官方文档，回答两个问题：AizenAssistant 当前有什么值得对外表达的差异，以及哪些只是规划、通用能力或技术实现。

## 结论

AizenAssistant 当前最值得强调的定位不是“功能最多的 Coding Agent”，而是：

> **一个强调上下文可控、过程可审计，并准备同时服务终端与桌面的 Agent 产品。**

从用户视角看，当前值得介绍的亮点不应只限于核心卖点：

1. **已实现：显式、可切换的“视图”上下文。**
2. **已实现：要求 Agent 说明每次工具调用目的，并保存结构化过程。**
3. **已实现：会话和视图使用便于记忆、口述和查找的三词 ID。**
4. **部分实现：会话以用户可见的单文件保存，可自行改名、备份和恢复；跨目录迁移仍需产品支持。**
5. **机制已实现、具体用途未交付：可审计的每轮额外消息管线。**
6. **值得规划：中断可解释的会话恢复，让 Agent 知道上次是用户中止还是异常退出。**

这些内容可按“核心能力”“体验细节”“正在建设”分组呈现，不需要人为只保留少数所谓核心卖点。

桌面 GUI、TUI/GUI 共用核心和无需 Node/Bun 的 Windows 分发是明确规划，可以单独放入“路线图”，但不能混入现有功能。

## 已实现的差异化候选

### 1. 视图：显式选择 Agent 的工作上下文

一个视图可以提供：

- `SYSTEM.md`；
- `AGENTS.md`；
- `skills/`。

用户可以创建、管理和切换视图。每轮请求前都会重新读取当前视图，因此修改文件后，下一轮即可生效。选择“无视图”时，程序明确不读取工作目录、父目录或用户目录中的同类资源。

这与主流的目录层级发现机制不同：

- pi 默认从用户目录、父目录和当前目录加载上下文文件与 Skill；
- Codex 从全局目录到当前工作目录构造 `AGENTS.md` 指令链；
- Gemini CLI 从全局、工作区和按需访问的目录层级加载 `GEMINI.md`；
- Aider 通常由用户手动或通过配置加载约定文件。

AizenAssistant 的价值不是“也支持系统提示词和 Skill”，而是：

- 上下文来源由用户显式选择，不由当前目录隐式决定；
- 同一项目可以在不同工作方式之间切换；
- 视图内容每轮重载，不必重启会话；
- “不加载项目上下文”也是明确、可复现的状态。

**判断：强差异化，但不应宣称全球唯一。** 其它 Agent 可通过配置、扩展或不同启动目录模拟部分效果；AizenAssistant 的特点是把它做成一等产品概念和会话设置。

**重要边界：** 会话只保存视图 ID，不保存当时的视图文件内容。视图后来被修改后，历史会话无法单独还原某一轮完整的系统提示词。因此它目前是“来源可控”，还不是“提示词内容完全可追溯”。

### 2. 工具调用目的：先说明为什么，再执行

AizenAssistant 的四个开发工具要求模型为每次调用提供不超过 50 个字符的 `declaredIntent`。TUI 会展示调用目的、参数摘要、运行状态和结果；该目的也会进入会话记录，但不会作为真实工具参数传给底层工具。

相较只展示命令、文件路径或审批对话，这让用户更容易理解 Agent 当前为什么读取文件、运行命令或修改代码。

**判断：较强差异化。** 本次查阅的 pi、Codex、Gemini CLI 和 Aider 官方说明中，未发现同等的“所有内置开发工具必须声明调用目的”产品约束。

**重要边界：** 调用目的由模型生成，只是审计线索，不保证真实、完整或正确；它不能替代权限控制和沙箱。

### 3. 自有结构化会话与可靠性

AizenAssistant 不直接把 pi 会话文件作为产品数据，而是保存自有版本化 JSONL，记录：

- 每轮实际输入；
- 助手文本和思考内容；
- 工具调用及结果；
- 模型来源、视图 ID 和轮次结果；
- 上下文压缩记录。

会话支持保存、恢复、命名、回退和独立分支。写入采用队列、跨进程锁和原子替换；摘要索引损坏时可以从 JSONL 重建。当前验证还覆盖并发写入、Windows 独占句柄、损坏尾行和落盘失败。

**判断：这是用户可以感知的可信度亮点，但不是独有能力。** pi 本身也保存完整 JSONL、支持压缩后保留原始历史，并拥有更完整的树状分支体验；Gemini CLI 还可通过检查点同时恢复文件和对话。README 可以直接强调“记录在本地、过程不因压缩而消失、出错后仍可恢复”，不必用 JSONL、锁或原子替换作为标题。

### 4. 助记 ID：会话不再是一串 UUID

会话和视图默认使用主谓宾三词 ID，例如 `otter-builds-bridge`。会话文件名同时包含本地创建时间和助记 ID，用户还可以给会话另取名称。

它的用户价值是：

- 在会话列表、文件管理器和终端标题中更容易辨认；
- 复制、口述或在支持沟通中引用时更少出错；
- 用户不命名会话时，仍然有一个可用身份；
- 自动处理同一目录内的 ID 冲突。

**判断：明确的体验亮点。** 它不会单独决定用户是否采用产品，但能持续降低管理成本，适合放在“贴心细节”或会话能力中。宣传语言应是“好记、好找、好交流”，而不是“实现了助记 ID 生成器”。

### 5. 会话文件归用户管理

当前每个会话是一个自包含的 JSONL 文件；图片直接内嵌，文件名不参与身份识别。因此用户可以在应用外：

- 修改文件名而不影响打开和续写；
- 复制到备份位置，之后放回原项目会话目录恢复；
- 使用普通文件工具同步、版本管理或归档。

但当前不能笼统宣传“随意复制到任何地方继续使用”：

- 应用只扫描当前工作目录对应的会话目录；
- 会话头保存原始 `cwd`，打开时要求与当前工作目录完全一致；
- 同目录出现相同会话 ID 会明确报错；
- 视图内容、模型配置和认证不包含在会话文件中。

工作目录绑定本身有意义：它防止用户误把针对 A 项目的历史和工具操作带到 B 项目执行。需要解决的不是取消安全边界，而是提供明确的**导入与重新绑定**能力：

1. 导入时校验完整会话，而不是让用户手工放文件；
2. ID 冲突时生成新助记 ID，并保留来源信息；
3. 原工作目录仍存在时默认恢复原绑定；
4. 原目录不存在时允许用户选择新目录，明确提示历史路径和工具结果来自旧目录；
5. 重新绑定后在下一轮向 Agent 提供一次结构化迁移说明；
6. 缺失的视图或模型只影响继续对话，不影响只读查看历史；
7. 后续可提供包含会话、视图快照和元数据的导出包，但认证密钥不得打包。

**判断：当前是“文件透明、易备份”，完成导入/重新绑定后才适合宣传“会话真正归你，可自由迁移”。**

## 机制已实现，但用户能力尚未交付

### 每轮额外消息

核心允许在每轮请求前生成零条或多条额外消息，并区分：

- `useLater: true`：进入当前请求，并保留到后续上下文；
- `useLater: false`：进入当前请求和会话记录，但不进入下一轮或恢复后的模型上下文。

该机制已通过核心和 pi adapter 测试。它适合承载记忆召回、用户偏好或临时任务判断，同时避免临时信息不断累积。

但生产 TUI 没有注入任何具体提供器，默认始终返回空数组。当前产品不会主动执行记忆召回或用户建模。

**对外表述建议：** “已建立每轮临时上下文机制；记忆召回等具体应用尚未提供。”不能写成“已经具备智能记忆”。

此外，pi 扩展本身也能在请求前注入消息或修改上下文；AizenAssistant 的潜在差异在于把“是否进入后续轮次”和“所有实际输入先落盘”固化为核心契约，而不是仅仅能够注入消息。

## 值得新增规划：中断可解释的恢复

目标应从用户语言定义：

> 应用意外关闭后，再次打开不只是回到历史记录；Agent 还应知道上次在哪里停下、为什么停下，以及哪些操作结果不能假定。

当前已能把正常完成、主动中止和请求失败写成不同的轮次结果。pi 在进程仍存活时也会把被中止的工具变成错误工具结果。但如果进程断电、崩溃或被系统强制结束，最后一轮只有 `turn_started` 而没有 `turn_finished`；恢复逻辑会把整个未完成轮次排除出模型上下文。因此当前只能由程序发现“不完整”，Agent 不会主动理解这次异常恢复。

建议采用以下设计：

1. **记录请求，而不是伪造原因。** 用户按下中止时，先落盘 `interrupt_requested`，原因记为 `user`；正常退出记为 `application_shutdown`。这只证明请求发生过，不证明工具已经停止。
2. **在副作用前建立持久化边界。** 工具真正执行前，核心先同步落盘 `tool_execution_started`，完成后落盘 `tool_execution_finished`。该事件必须等待 `fsync` 后才允许执行，不能继续使用当前不等待落盘的界面事件。
3. **恢复时推断，保留确定性。** 有用户中止请求则显示“用户已请求中止”；有工具开始而无结束则显示“工具可能已执行，结果未知”；没有任何结束请求则显示“应用或系统异常终止，具体原因未知”。断电、进程崩溃和强制结束无法仅靠会话文件进一步区分。
4. **向用户和 Agent 同时解释。** 恢复时追加结构化 `recovery_observed` 记录，并在下一轮注入一次临时 developer 消息：说明中断类别、未完成工具及“不要自动重试，应先检查状态或询问用户”。
5. **不承诺任意工具的恰好一次执行。** 对 `bash` 和外部系统操作，崩溃可能发生在副作用完成与完成记录落盘之间，只能标记“结果未知”。对 `write`、`edit` 可额外保存目标路径和前后哈希，恢复时检查文件状态，从而给出更强判断。
6. **区分关闭方式。** 桌面 sidecar 上线后，由 GUI 记录用户关闭、sidecar 异常退出和操作系统终止信号；无监督的断电仍归类为“非正常终止”。

推荐的最小记录模型是：

- `interrupt_requested`：谁请求了中断、何时请求；
- `tool_execution_started` / `tool_execution_finished`：工具是否跨过执行边界；
- `turn_finished.cause`：`user_abort`、`runtime_error`、`graceful_shutdown`；
- `recovery_observed`：恢复时基于现有证据得出的结论和确定性。

多数主流 Agent 支持中止、恢复、错误工具结果或检查点，但本次官方资料没有发现它们普遍承诺“崩溃后向 Agent 结构化说明中断来源和未完成副作用”。pi 已提供主动中止的底层语义，但也没有替 AizenAssistant 完成跨进程崩溃日志。因此这可以成为真实差异，但必须以故障注入测试证明，不能只靠设计宣称。

## 明确规划中的能力

根据现有路线图，后续计划是：

1. 建立版本化 JSONL 桌面协议和 `core-sidecar`；
2. 建立 Vue + Tauri 桌面最小闭环；
3. 让桌面端复用当前 TypeScript 核心，获得与 TUI 一致的会话、模型、视图和工具行为；
4. 完善长会话、长工具输出、中文输入、窗口缩放和状态反馈；
5. 完成无需用户安装 Node/Bun 的 Windows x64 分发验收。

这些内容可以写入“规划”章节。它们目前不是可用功能，也没有公开交付日期。

“调用小模型进行用户心智建模和记忆召回”目前只是技术方案中的用途示例，不是已有实现，也没有独立里程碑承诺，不宜写成确定规划。

## 完整功能中并非独有的能力

以下能力仍应写入完整功能介绍，但不应被包装成独有能力：

- 基于 pi SDK、TypeScript、OpenTUI、Tauri；
- 多模型、多供应商和自定义 Base URL；
- 流式回复、工具执行、中止、上下文用量；
- 会话恢复、回退、分支和压缩；
- Skill、`AGENTS.md` 和系统提示词；
- 单文件可执行程序。

它们适合出现在功能清单、兼容性或安装说明中，不应占据 README 的定位区。

尤其是回退与分支：pi 的树状会话比当前 AizenAssistant 更完整；Gemini CLI 的检查点还能恢复文件。AizenAssistant 的回退不会撤销工具对文件或外部系统造成的副作用。

## 当前文档问题

1. `README.md` 只反映了较早期状态，遗漏视图管理、工具目的、思考档位、模型管理、会话回退和分支等能力。
2. `docs/AizenAssistant技术路线图.md` 仍称 M3 未实施，但相关功能已在提交 `2b7d8d1` 完成。
3. README 把桌面 GUI 与现有 TUI 并列描述，容易让读者误以为 GUI 已可用。
4. README 写有 `--plain` 用法，但该入口已在提交 `e229e83` 删除。

因此，在重写面向用户文档前，应先校准“当前功能”和“规划功能”，否则 README 会继续产生错误预期。

## 建议的 README 信息顺序

1. 一句话说明用户得到什么：可选择 Agent 的工作方式，看得懂它为什么行动，并掌握自己的会话记录；
2. “为什么选择 AizenAssistant”：视图、工具调用目的、本地完整记录；
3. “使用中的贴心细节”：助记 ID、会话命名、回退与分支、状态与用量展示；
4. “你的数据”：会话如何保存、目前能怎样备份、迁移能力的现状；
5. “正在建设”：中断可解释恢复、桌面 GUI、TUI/GUI 一致体验和 Windows 分发；
6. 快速开始、完整功能、限制和开发文档。

宣传标题应先说用户收益，再用技术事实证明。例如：

- “为不同任务切换不同工作方式”，而不是“视图式资源加载”；
- “每次操作都告诉你为什么”，而不是“`declaredIntent` 字段”；
- “会话好记、好找、可自行备份”，而不是“主谓宾 ID 与 JSONL”；
- “意外中断后，知道哪里没做完”，而不是“恢复日志和落盘协议”。
