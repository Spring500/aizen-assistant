# 自举套件使用说明

本文说明 Aizen 的自举套件：它解决什么问题、如何启动、如何用一句话指挥模型做出你想要的行为，以及它验证不了的地方。

阅读本文不需要了解 Aizen 内部实现。面向维护者的接口契约与扩展方式另见[《自举套件实现规格》](自举套件-实现规格.md)。

---

## 1. 它是什么

自举套件让你**不连接任何真实模型服务、不配置任何真实凭据**，就能完整启动 Aizen 并手工操作。

它由两部分组成：

| 组成 | 作用 |
|---|---|
| Mock Server | 本地 HTTP 服务，冒充模型服务商，按请求中的模型 ID 决定如何回应 |
| Mock Data 套件 | 一份完整的应用数据（虚拟供应商、虚拟模型、视图、偏好），其中所有模型都指向 Mock Server |

一条命令同时启动两者：

```powershell
bun run dev:mock
```

它的核心特点是：**模型的行为由你在聊天框里现场指定**。你不需要预先配置"这次要模拟工具调用"，直接把要求写进对话即可。

**它是开发与验证工具，不是模型模拟器。** 它不试图让回复看起来像真模型，只保证协议层面完全合法、行为完全可控可复现。这个区别决定了它能做什么，第 6 节会具体说明。

---

## 2. 快速开始

### 2.1 启动

```powershell
bun run dev:mock
```

这条命令会依次完成：

1. 在 `127.0.0.1:39527` 启动 Mock Server；
2. 把 `default` 套件复制到工作区根目录的 `mock-data/`；
3. 用 `mock-data/` 作为数据目录启动 TUI。

退出 TUI 时 Mock Server 一并关闭。

### 2.2 第一次对话

启动后新建会话，默认模型已是 `mock-dsl`。在输入框里写：

```
think 让我想想
text 你好，这是一次完整的模拟回复。
```

你会看到思考区展示"让我想想"，回复区展示后面那句话。**你写的不是问题，是这一轮模型该做什么的指令。**

如果输入无法解析为指令，模型会原样回显，并附带完整解析错误：

```
用户输入无法解析，原样输出结果如下：
<你的原文>

解析错误：
<错误信息>
```

看到这段提示，就说明指令写错了，对照第 4 节检查语法。

### 2.3 常用参数

| 命令 | 作用 |
|---|---|
| `bun run dev:mock` | 用 `default` 套件启动，重置 `mock-data/` |
| `bun run dev:mock <套件名>` | 指定套件启动 |
| `bun run dev:mock --keep` | 保留上次的 `mock-data/`，不重置 |

**默认每次启动都会重置 `mock-data/`。** 上一次的会话记录、改动过的配置都会丢失。需要接着上次继续时加 `--keep`。

套件名写错时会列出所有可用套件。端口 39527 被占用时直接报错退出，不会换端口——套件里的地址是写死的，换端口会导致连不上。

## 3. Mock Data 套件

套件是一份**完整自包含**的应用数据。切换套件就是切换整套配置：供应商、模型、视图、偏好、子 Agent 指向。

模板存放在 `tests/fixtures/mock-data-templates/<套件名>/`，随版本库入库。启动时复制到工作区根目录的 `mock-data/` 运行，该目录不入库。

**要修改配置，改运行实例 `mock-data/` 即可，随时可弃；要让改动长期生效，改模板。** 模板改动会进入版本库，请谨慎。

### 3.1 default 套件

首个套件 `default` 提供三个虚拟模型，分别对应一种行为：

| 模型 ID | 行为 |
|---|---|
| `mock-dsl` | 把你的输入当指令执行（第 4 节） |
| `mock-naming` | 生成会话标题：时间戳 + 关键字 |
| `mock-review` | 按暗语裁决工具权限（第 5 节） |

每个模型都提供 `anthropic-messages` 和 `openai-completions` 两种协议的条目，可在模型选择器中切换。两者行为完全一致，区别只在通信协议，用于验证两条协议链路。

`default` 套件的偏好配置：

- 新会话模型：`mock-anthropic/mock-dsl`；
- 会话命名 Agent：`mock-anthropic/mock-naming`；
- 权限审核 Agent：`mock-anthropic/mock-review`；
- 默认视图：`mock-default`；
- `auth.json` 含仅本地使用的占位凭据，使六个 Mock 模型启动即为可用状态。

### 3.2 新增套件

在 `tests/fixtures/mock-data-templates/` 下新建一个目录，放入完整的应用数据即可，无需改动任何代码。套件之间不共享内容，也没有继承或合并机制——每份自包含，改一份不会影响另一份。

## 4. 指令语法

`mock-dsl` 模型把你输入的**最后一条消息**解析为指令，逐条执行。

### 4.1 基本形式

每行一条指令，格式为：

```
<动词> <参数>
```

工具类指令多两个字段：

```
<工具名> <调用名> <意图> | <参数>
```

- **调用名**：你给这次工具调用起的名字，用于后面引用它的结果，如 `T1`、`读配置`。同一次输入内不可重复。
- **意图**：这次调用的目的，会显示在权限审核界面。超过 50 个字符会自动截断。
- `|` 之前是意图，之后是工具参数。意图和参数都可以包含空格。

### 4.2 动词一览

| 动词 | 形式 | 作用 |
|---|---|---|
| `think` | `think <文本>` | 输出思考内容 |
| `text` | `text <文本>` | 输出回复文本 |
| `bash` | `bash <名> <意图> \| <命令>` | 调用 bash 工具 |
| `read` | `read <名> <意图> \| <路径>` | 调用 read 工具 |
| `write` | `write <名> <意图> \| <路径>` + 内容块 | 调用 write 工具 |
| `edit` | `edit <名> <意图> \| <路径>` + 编辑块 | 调用 edit 工具 |
| `delay` | `delay <毫秒>` | 暂停指定时间后继续 |
| `error` | `error <状态码> [消息]` | 返回初始 HTTP 错误；前面只能有 `delay`，且必须最后一条 |
| `disconnect` | `disconnect [消息]` | 已开始输出后的 SSE 连接异常中断；必须最后一条 |
| `hang` | `hang` | 不再响应，直到你取消；必须最后一条 |

### 4.3 多行文本

`text` 和 `think` 的内容需要换行时，用 `<<<` 和 `>>>` 包起来：

```
text <<<
第一行
第二行
>>>
```

`write` 的文件内容必须用块：

```
write W1 写入配置 | config.json
<<<
{"enabled": true}
>>>
```

`edit` 用嵌套块表达替换前后的文本，`old` 与 `new` 成对出现，可以有多对：

```
edit E1 调整配置 | config.json
<<<
old <<<
"enabled": false
>>>
new <<<
"enabled": true
>>>
>>>
```

### 4.4 引用工具结果

用 `{{调用名.Result}}` 引用某次工具调用的返回内容：

```
bash T1 列出当前目录 | ls
text 目录内容是：{{T1.Result}}
```

仅 `think` 和 `text` 支持 `{{调用名.Result}}`。工具命令、路径、写入内容和编辑块中的同样文本均按普通字面量处理。

**引用会自动切分轮次。** 上面这段的实际执行过程是：

1. 第一轮：模型发起 `T1` 调用，本轮结束；
2. Aizen 执行 bash，把结果交回模型；
3. 第二轮：模型输出文本，`{{T1.Result}}` 已被替换为真实结果。

你不需要关心这个过程，按顺序写下你想要的效果即可。连续的工具调用之间若无引用，会在同一轮一起发出：

```
bash T1 查看状态 | git status
bash T2 查看分支 | git branch
text 状态：{{T1.Result}}
分支：{{T2.Result}}
```

`T1` 和 `T2` 在同一轮并行发出，文本在下一轮输出。

### 4.5 完整示例

模拟一次带思考、多步工具、最后总结的完整回合：

```
think 先看看项目里有什么
bash T1 [通过] 列出项目根目录 | ls
read R1 [通过] 读取说明文档 | README.md
text <<<
目录内容：
{{T1.Result}}

文档开头：
{{R1.Result}}
>>>
```

模拟已输出思考后的连接中断：

```
think 正在处理
delay 2000
disconnect 上游连接中断
```

`error` 是 HTTP 状态码错误，不能出现在思考、文本或工具调用之后；上述场景应使用 `disconnect`。

## 5. 权限审核暗语

`mock-review` 模型不看工具参数，只看**意图字段里的暗语**决定裁决结果：

| 暗语 | 裁决 |
|---|---|
| `[通过]` | 放行 |
| `[拒绝]` | 拒绝 |
| `[人工]` | 转人工审核 |
| 无暗语 | 转人工审核 |

于是一条输入就能同时覆盖三条权限路径：

```
bash T1 [通过] 列出目录 | ls
bash T2 [拒绝] 删除文件 | rm -rf tmp
bash T3 检查状态 | git status
```

`T1` 自动放行，`T2` 自动拒绝，`T3` 弹出人工审核界面。

暗语只在权限审核模型面前生效，它同时也是意图文本的一部分，会原样显示在审核界面上。

需要注意：暗语能否生效，取决于这次调用是否真的走到了 AI 审核环节。权限预设和审核方式决定哪些调用需要审核、由谁审核，具体见[《权限系统使用说明》](权限系统-使用说明.md)。若当前设置下某次调用被直接放行或直接拒绝，暗语不会被读到。

## 6. 它验证不了什么

自举套件保证协议合法与行为可控，但以下方面无法通过它验证：

**模型能力相关的一切。** 回复质量、指令遵循程度、工具选择是否合理——这些取决于真实模型，Mock 只是照着你的指令执行。

**真实服务商的差异行为。** 限流、鉴权失败、区域性错误、各服务商对协议的私有扩展，Mock Server 不模拟。`error` 动词只能构造 HTTP 状态码层面的错误。

**性能与并发表现。** Mock Server 在本地同进程运行，没有真实网络延迟与吞吐限制。`delay` 只能构造固定延迟，不反映真实网络抖动。

**跨会话的模型记忆。** Mock 完全无状态，每次请求只看当轮的对话历史，与真实服务一致，但也意味着不能用它验证任何依赖服务端会话状态的设想。

因此，自举套件适合验证 Aizen 自身的交互、渲染、权限、会话管理与协议适配，不适合评估模型效果或替代真实链路的联调。
